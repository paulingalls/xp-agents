# Architecture

## Goals

1. **XP practices are enforced, not suggested.** Hooks make it structurally impossible to skip TDD, pair review, or customer feedback — agents don't need discipline, the system provides it.
2. **Shared understanding without coordination cost.** The broadcast event log (SMM) gives every agent full project context without point-to-point messaging or handoff ceremonies.
3. **Zero friction to adopt.** One install command, no config files, no workflow changes. It works because hooks fire automatically.
4. **Honest signal over noise.** Every event in the SMM earns its place. The system tracks what's unresolved, contradicted, or stale — not just what's been said.

## Core Concept

Hooks-driven Claude Code plugin. XP practices enforced through hook handlers, not agent compliance. Broadcast event log replaces point-to-point mailboxes.

## SMM Storage

```
~/.claude/xp-agents/{project-id}/smm/
├── events.jsonl              ← append-only, one JSON event per line
├── SHARED_MENTAL_MODEL.md    ← materialized view, auto-generated
├── .watermark-{agent-id}     ← per-agent read position
├── events.lock               ← flock for atomic appends
└── retrospectives/           ← Keep/Fix/Try session artifacts (.json)
```

User-level storage, per-project isolation. `project-id` derived from `git rev-parse --git-common-dir`. Shared across worktrees and Agent Team teammates. Install at user scope (`--scope user`).

## Event Types

| Type | Generated By | Purpose |
|---|---|---|
| `goal` | Agent (customer proxy, first-run) + customer | Project north star — what we're building and why |
| `customer_input` | Hook (UserPromptSubmit) | User's exact prompt — the customer's voice |
| `customer_intent` | Agent (customer proxy) | Distilled customer request — open / delivered / superseded. `source_refs` links to originating `customer_input` events |
| `status` | Hook (PostToolUse, auto) + agent | What's happening, `working_on` files |
| `decision` | Agent (prompted by hooks) | Architectural choices |
| `convention` | Agent | Team standards |
| `concern` | Hook (quality reviewer) + agent | Problems needing attention |
| `discovery` | Agent | Unexpected findings |
| `question` | Agent | Customer input needed: 🔴 blocking, 🟡 assumed, 🟢 informational |
| `assumption` | Agent | Stated beliefs — escalates if contradicted |
| `debt` | Agent (quality reviewer, retrospective) | Acknowledged tradeoff — known issue, chosen to live with for now |
| `pair_guidance` | Hook (navigator) | Strategic direction before writes |
| `session_end` | Hook (SessionEnd) | Duration, unresolved items, working_on at close, final status flag |
| `retrospective` | Hook (SessionStart, agent) | Keep/Fix/Try analysis |

🔴/🟡 heuristic: default to 🟡 with stated assumption. Use 🔴 only when both paths create significant rework.

## Materialized View Spec (SHARED_MENTAL_MODEL.md)

`materialize.py` generates this from `events.jsonl`. Two-tier structure: Active Context (needs attention now) above Reference (informs decisions). Sections with no content are omitted.

```markdown
# Shared Mental Model
*Auto-generated from events.jsonl ({n} events, {n} agents)*

---
## ACTIVE CONTEXT
---

## Project Goals
- 🎯 {goal description} [{agent}, {id}]
(Pinned. Also extracted from project CLAUDE.md if present.)

## Conflict Alerts
- ⚠️ working_on overlap: {agent-a} and {agent-b} both claim {file}
- ⚠️ assumption contradicted: {id} contradicted by {id}
- ⚠️ convention violation: decision {id} diverges from convention {id}

## Drift Signals
- ⚠️ Convention "{name}" [{id}] — {n} concern events since established
- ⚠️ Decision "{name}" [{id}] — no related activity in {n} sessions
- ⚠️ Superseded: decision {id} and {id} both address {topic}
(Event-log-only analysis. No codebase I/O.)

## Blocking Questions
- 🔴 {question} [{agent}, {id}] — **awaiting answer**

## Unacknowledged Concerns
- ⚠️ {description} [{agent}, {id}]

## Customer Intent
- 📋 {description} [{id}] — from {source_refs}
(Open items only. Delivered/superseded items removed from view.)

## Agent Status
- **{agent}**: {latest status content}. Working on: {files}
- **{agent}**: {latest status content}. Idle.

## Navigator Guidance
- {guidance} [{id}, for {agent}]
(Current session only. Cleared on session start.)

---
## REFERENCE
---

## Architecture Decisions
- **{summary}** [{agent}, {id}, references {id}]
- (draft) **{summary}** [{agent}, {id}] ← auto-drafted, needs review

## Conventions
- {description} [{agent}, {id}]

## Questions (Resolved & Assumed)
- 🟡 {question} [{agent}, {id}] — **assumed: {assumption}**
- ✅ {question} [{agent}, {id}] — answered: {answer} [{id}]

## Discoveries
- ⚠️ {description} [{agent}, {id}]

## Assumptions
- {description} [{agent}, {id}] — unverified
- ❌ {description} [{agent}, {id}] — contradicted by {id}

## Technical Debt
- {description} [{agent}, {id}] — acknowledged, rationale: {why}, 2 sessions old
- ⚠️ {description} [{agent}, {id}] — acknowledged, rationale: {why}, 7 sessions old, escalating
- ✅ {description} [{agent}, {id}] — resolved → {id}

- ✅ {description} [{agent}, {id}] — resolved → {id}
```

**Design notes:** Active Context is what gets injected for non-write tools (minimal tier). Full SMM including Reference is injected for write tools. Goals are pinned at the top always — they're the north star every decision is measured against. Navigator guidance is scoped to current session only to prevent stale advice. Raw customer prompts are no longer materialized — strategic intent is captured through `goal` events, tactical intent through `customer_intent` events distilled by customer proxy at session start.

### Debt Aging & Repayment Pressure

Debt age is computed at materialize time by counting `session_end` events after the debt event's timestamp. No event mutation — append-only log is preserved. Escalation thresholds:

- **0–3 sessions**: rendered normally, no marker
- **4–6 sessions**: rendered with ⚠️, retrospective analyst flags in Fix items
- **7+ sessions**: rendered with 🔴, retrospective analyst escalates urgency

Repayment pressure comes from three hooks, not a single enforcement point:

- **Navigator**: when an agent modifies a file associated with a debt event, navigator guidance includes "debt exists in this file — address it or state why not"
- **Quality reviewer**: if an agent touches a file with associated debt and doesn't address it, reviewer writes a `concern` event
- **Retrospective analyst**: aging debt appears in Fix items with increasing urgency. Debt referenced by multiple concerns gets highest priority.

### Session Stats & Plugin Observability

`retrospective.py` computes session stats from the event log and includes them in `.retro-input.json`. The retrospective analyst uses these stats to flag plugin health anomalies in its Keep/Fix/Try analysis. No new event types, no new hooks — just counting what's already there.

**Stats computed from event log:**

| Stat | What It Reveals |
|---|---|
| Events by type | Overall system activity |
| Pair guidance count vs. file writes | Navigator effectiveness — 0 guidance with many writes means self-filtering may be too aggressive |
| Concerns raised vs. resolved | Whether quality reviewer feedback is being addressed |
| Questions open vs. answered | Stale questions accumulating |
| Conflicts detected (by pattern) | Which conflict patterns are firing |
| Customer intents open vs. delivered | Whether customer requests are being tracked and completed |
| Decisions (draft vs. confirmed) | Whether the team is recording architectural choices |

**Anomaly patterns the analyst flags:**
- 0 pair_guidance with >0 file writes → navigator may not be effective
- High unresolved concern ratio → concerns not being addressed
- Many file writes with 0 concerns → either genuinely clean code or reviewer not catching issues
- 0 decisions despite significant work → decisions not being recorded
- Cross-session trends → stats compared against previous retrospectives for trajectory

### First-Run Behavior

When `session_start.py` initializes a new SMM (no prior `events.jsonl`), `customer_proxy.md` detects the empty state and asks via `AskUserQuestion`: "What's the goal of this project? What are you trying to build and why?" Response is recorded as a `goal` event. Non-blocking — the customer can skip and it becomes a 🟡 question re-asked next session.

## Injection Architecture

### How Context Reaches Agents

| When | Hook | What's Injected |
|---|---|---|
| Session start | SessionStart | Full SMM (after retrospective if applicable) |
| Subagent spawn | SubagentStart | Full materialized SMM |
| Before tool use | PreToolUse | Delta since agent's watermark (tiered) |
| After compaction | SessionStart (compact matcher) | Full SMM re-injection |

All injection via `additionalContext` in hook JSON output. Never in system prompt (preserves prompt cache).

### Prompt Cache & Token Cost

**Cache safety.** `additionalContext` appends after the cached prefix (system prompt, CLAUDE.md, conversation history). It never inserts into the prefix. Prompt cache is preserved across all hook injections.

**Token cost model:**

| Source | Per-occurrence | Frequency | Mitigation |
|---|---|---|---|
| PreToolUse delta (full) | 50–500 tokens | Every Write/Edit/Commit | Watermarks ensure no duplicates; only new events |
| PreToolUse delta (minimal) | 10–50 tokens | Every other Bash/Read/Grep | 🔴 questions only — nearly free |
| Navigator agent hook | 5,000–10,000 tokens (subagent) | Every Write/Edit | Self-filters trivial changes in prompt (fast exit, minimal tokens) |
| Quality reviewer agent hook | 5,000–10,000 tokens (subagent) | Every Write/Edit (async) | Async — doesn't block; cost is real |
| SessionStart full SMM | 2,000–5,000 tokens | Once per session | One-time cost |
| Retrospective analyst | 10,000–20,000 tokens (subagent) | Once per session | Only when unanalyzed events exist |
| Customer proxy | 5,000–10,000 tokens (subagent) | Once per session | Only when open questions exist |

**Cost control levers:** Navigator self-filtering (trivial changes get fast exit with minimal tokens), tiered injection (reduces delta size for non-write tools), async PostToolUse hooks (no latency cost, only token cost), watermarks (no duplicate events).

### Tiered Injection

| Tool | Level |
|---|---|
| Write, Edit, MultiEdit | Full delta (Active Context + Reference) |
| Bash (git commit) | Full delta |
| Bash (other) | Active Context only (goals, conflicts, 🔴 questions, concerns) |
| Read, Grep, Glob | 🔴 questions only |

### Per-Agent Watermarks

`agent_id` from hook input (absent = `main`). Each agent tracks its own read position: `.watermark-main`, `.watermark-{agent_id}`.

## Conflict Detection

Two tiers. Best-effort by design.

**Tier 1 — Structural (deterministic).** `post_tool_use.py` on event appends:

| Pattern | Method |
|---|---|
| Overlapping `working_on` | Array comparison across status events |
| Assumption contradicted by discovery | Reference chain traversal |
| Convention violation | Decision references convention but diverges |
| Stale question | No answer after N events |
| Superseded decision | Two decisions, same topic, no concern between |

Critical → exit 2 (block) in `strict` mode, warning via additionalContext in `advisory` mode. Non-critical → event log warning.

**Tier 2 — Semantic (via additionalContext).** On `decision`/`convention` append, include recent decisions in next PreToolUse for agent to review.

## Session Flows

### Session Start
```
SessionStart → command: init, retro check, SMM injection, GUPP, skills
            → agent: retrospective-analyst (if unanalyzed events)
            → agent: customer-proxy (if open questions)
            → work begins
```

### Mid-Session
```
PreToolUse  → command: delta injection, conflict blocking, TDD order check
            → agent: navigator (Write/Edit only, self-filters trivial changes)
Tool executes
PostToolUse → command: auto status, conflicts, lint
            → agent (async): quality reviewer (Write/Edit)
            → command: bash analysis (Bash)
```

### Session End
```
SessionEnd  → command: append session_end event (non-blocking)
```

### Subagent Lifecycle
```
SubagentStart → command: SMM injection + watermark
Subagent works (hooks fire normally)
SubagentStop  → command: record work, conflicts, delta
              → command: plan review (Plan agent only)
              → agent (async): holistic review
```

## XP Practices Enforcement

| Practice | Enforcement | Mechanism |
|---|---|---|
| **TDD** | Deterministic: Stop blocks if tests fail. LLM: navigator flags implementation-before-tests. | `tdd_check.md`, `pre_tool_use.py` |
| **Pair Programming** | LLM (required): navigator before every significant write, quality reviewer after. | `navigator.md`, `quality_reviewer.md` |
| **Planning Game** | LLM + deterministic: plan review extracts decisions/assumptions, flags oversized plans. Customer-proxy triages questions. | `plan_review.py`, `customer_proxy.md` |
| **Small Releases** | Deterministic: commit size check. LLM: navigator nudges when no recent commits. | `bash_post_tool.py` |
| **Coding Standards** | Deterministic: lint after every write, convention tracking in SMM, conflict detector catches violations. | `lint_check.py`, `post_tool_use.py` |
| **Continuous Integration** | Deterministic: test results parsed and recorded. Stop blocks on failure. | `bash_post_tool.py`, `tdd_check.md` |
| **Refactoring** | LLM: quality reviewer flags growing complexity. Retrospective tracks unfixed flags. | `quality_reviewer.md` |
| **Simple Design** | LLM: quality reviewer flags over-engineering. Plan review flags oversized plans. | `quality_reviewer.md`, `plan_review.py` |
| **Collective Code Ownership** | Deterministic: SMM injected into all agents automatically. Global hooks. | `pre_tool_use.py`, `subagent_start.py` |
| **On-Site Customer** | Deterministic: prompts logged, notifications sent. LLM: customer-proxy triages questions. | `user_prompt_log.py`, `customer_notify.py`, `customer_proxy.md` |
| **Standup** | Deterministic: auto-generated status/working_on from tool calls. Continuous. | `post_tool_use.py` |
| **Retrospective** | LLM (required): Keep/Fix/Try at session start. XP values as analytical lenses. | `retrospective_analyst.md` |
| **Sustainable Pace** | Deterministic: SMM survives compaction, session_end preserves state. | `pre_compact.py`, `session_end.py` |

Practices we can't enforce: System Metaphor (emerges from use), Move People Around (agents don't persist).

## Agent Teams

SMM at `~/.claude/xp-agents/{project-id}/smm/` is shared across all worktrees and teammates. Because hooks are global:

- Every teammate gets SMM deltas before every tool call
- Every teammate's code is reviewed by quality reviewer and navigator
- Every teammate's `working_on` is tracked for conflict detection
- Every teammate's decisions are visible to all others
- Retrospective analyzes the whole team's session

### Verification needed during development:
- User-level plugin hooks fire for Agent Team teammates
- Concurrent `events.jsonl` writes from multiple teammates (flock)
- `agent_id` differs per teammate (needed for watermarks)
- SessionStart fires for each teammate

## Platform Constraints

### Confirmed
- PreToolUse `additionalContext` → injected into agent context (v2.1.9+)
- SessionStart/SubagentStart `additionalContext` → injected into context
- `agent_id`/`agent_type` in hook input for subagents (v2.1.9+)
- Async hooks deliver context on next turn

### Not Confirmed
- PostToolUse `additionalContext` → may not reach agent without `decision: "block"`. ([#18427](https://github.com/anthropics/claude-code/issues/18427), [#24788](https://github.com/anthropics/claude-code/issues/24788), [#31301](https://github.com/anthropics/claude-code/issues/31301))
- Agent hook rich output beyond allow/block → undocumented

**Design consequence:** PostToolUse hooks record to event log. PreToolUse hooks deliver via `additionalContext`. Test PostToolUse `additionalContext` during development; optimize if it works.

## Adoption & Compliance

### Hooks enforce (no agent compliance needed):
SMM injection, status/working_on tracking, code review, navigation, conflict detection, customer input logging, session bookkeeping, retrospective, TDD stop gate, lint enforcement, plan review.

### Agent compliance needed (with mitigations):
- **Decision recording** — hooks prompt, planned mitigation: auto-draft decisions from commits
- **Event quality** — planned mitigation: PreToolUse nudges for vague events
- **Judgment events** (assumptions, questions, discoveries) — CLAUDE.md rules, quality reviewer catches some gaps
- **Final status at session end** — CLAUDE.md rule, session_end flags when missing

## Error Handling

Fail loud, never corrupt, always recoverable.

| Scenario | Behavior |
|---|---|
| Malformed event | Materializer skips, emits concern |
| Unknown event type | Rendered under "Unknown Events" |
| SMM directory missing | Hooks pass through, next SessionStart recreates |
| Materializer crash mid-write | Atomic write via tempfile + rename |
| Lock timeout (>2s) | Append without lock, log warning |
| Retrospective on <5 events | "Insufficient data" |
| Python not found | Clear error at init, exit 1 |
| Schema validation failure | Append rejected, stderr error |
| Agent hook on xp-agents subagent | Skip (recursion prevention) |

## Implementation Notes

- **PostToolUse agent hooks should run async** — feedback goes through event log anyway
- **Navigator self-filtering** — command hooks cannot gate/skip subsequent agent hooks in the same matcher array, so significance filtering is done in the navigator prompt itself. Trivial changes (whitespace, comments, single-line renames) get an immediate empty response.
- **Navigator writes `pair_guidance` events** to event log for retrospective analysis, not just ephemeral additionalContext
- **Performance budget** — 2 agent hooks per Write/Edit (navigator + quality reviewer). Navigator self-filters trivial changes for minimal token cost.

## Design Principles

1. Hooks enforce, agents suggest
2. Broadcast over point-to-point
3. Zero dependencies (Python stdlib only)
4. Communication substrate, not orchestrator
5. Crash-safe by construction
6. Physics over politeness (GUPP)
7. Decisions survive compaction
8. Command hooks for determinism, agent hooks for judgment
9. Global hooks, automatic participation
10. Use the platform, don't fight it
11. The customer's voice is in the log

## Future Vision: Autonomous Teams (2.0)

1.0 assumes a human in the loop at every decision point. 2.0 loosens that assumption. The SMM already tracks goals, decisions, debt, and concerns — 2.0 adds a work queue and lets Agent Teams execute against it with minimal human intervention.

**Backlog.** New `backlog_item` event type: priority, acceptance criteria, dependencies, status (ready / in-progress / done / blocked). The planning game becomes a SessionStart activity — customer proxy reviews the backlog, picks the next ready item, assigns it. For Agent Teams, the planner distributes items across teammates based on dependencies and working_on state.

**Burn down.** Materializer renders backlog progress: items completed vs. remaining, velocity (items per session), projected completion. Feeds into retrospective for trend analysis.

**Autonomous planning game.** Plan reviewer checks plans against the backlog — is this the right next item? Does it respect dependencies? Is it right-sized? The 🟡 assumption mechanism handles ambiguity: the system assumes and proceeds, escalating to 🔴 only when risk is high.

**Requirements as input.** A requirements document dropped into the project gets decomposed into backlog items at SessionStart. Customer confirms priority once. After that, the team works the backlog session after session, asking the customer only for 🔴 decisions.

**Draft decision lifecycle.** Not all decisions need human approval. 1.0 already auto-drafts decisions from commits (`draft: true`). 2.0 gives drafts a lifecycle: drafts with no concerns after N sessions get **promoted** to confirmed (the `(draft)` prefix drops). Drafts that accumulate concerns get **escalated** to 🔴 questions for customer review. This is the same aging pattern as debt, applied in reverse — time without problems builds confidence. Conventions can gate specific domains ("all auth decisions require approval"), enforced by navigator and plan reviewer. The retrospective analyst closes the feedback loop: if draft decisions keep getting revised, it surfaces a Fix recommending more customer involvement in that area. No numeric confidence threshold to tune — the existing event types (decision, concern, convention) already carry the signal.

**Blocks as maturity signal.** In 1.0, three things can block: TDD check (tests failing), working_on conflicts (two agents on the same file), and navigator (decision contradictions). These blocks aren't friction — they're the system reporting that agents aren't yet coordinated enough for autonomy. When blocks stop firing because the system genuinely doesn't need them — tests always pass, agents never overlap, decisions are consistent — that's the readiness signal for 2.0. A mature SMM with well-coordinated agents produces the same behavior under `strict` and `advisory` enforcement, because nothing needs to block. The `enforcement` setting in `settings.json` (`strict` default, `advisory` available) lets users opt out of blocking early, but the goal is to make it unnecessary.

**What 1.0 provides that 2.0 needs:** goal tracking, decision recording, convention enforcement, debt aging, conflict detection, retrospectives, drift signals, velocity signal, session stats. The autonomy layer sits on top — it doesn't replace the XP enforcement, it leverages it.
